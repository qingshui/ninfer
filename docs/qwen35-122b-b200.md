# Qwen3.5-MoE-122B（NVFP4）B200 部署与验证指南

本文给出 Qwen3.5-MoE-122B 在单卡 B200 上从编译、权重转换、服务部署到正确性与性能验证的完整流程。命令中的机器相关路径全部是变量或占位符，按你的环境替换；仓库与脚本本身不依赖任何固定路径。

文中引用的基线数字来自 2026-11 的两轮优化交付：第一轮提交 `3a61e41f`（官方端到端验收 95.26 req/s，sglang 基线 61.0 的 1.56 倍），第二轮提交 `4ab8b02a`（TPOT 与定批 decode 全面优于 sglang，prefill 不退化）。测量机为 8×B200（每卡 183 GB），单卡完成全部验收；硬件与驱动见第 1 节。本模型无 MTP 与视觉组件，全部命令的投机模式都是 `mtp0`（不启用投机解码）。

## 0. 环境变量

除特殊说明外，本文命令都从仓库根目录执行，并假设先设置：

```bash
cd /path/to/ninfer                                  # 仓库根目录
export CUDACXX=/path/to/cuda/bin/nvcc               # nvcc 不在 PATH 时必须设置
export ARTIFACT=/path/to/qwen35-122b.ninfer          # 模型 artifact（第 3 节生成，或已备好）
export GPU=0                                        # 目标 GPU 序号，多卡机器按需修改
export PORT=8080                                     # 服务监听端口
```

构建产物在 `build/b200-release/` 与 `build/b200-dev/` 下，路径相对仓库根目录。

## 2. 编译

`b200-release` 产出服务与工具程序，是部署与验收用的构建；`b200-dev` 额外开启测试与 op 基准，用于正确性验证。

```bash
cmake --preset b200-release && cmake --build build/b200-release --parallel
cmake --preset b200-dev      && cmake --build build/b200-dev      --parallel
```

- 服务与验收只依赖 `b200-release`：产物为 `build/b200-release/apps/ninfer-serve`、`apps/ninfer`、`apps/ninfer-perplexity`。
- 请从构建树运行程序；移动产物时保持 `lib/` 与 `apps/` 同级。没有可安装的 C++ SDK。
- 既有问题：`b200-dev` 构建可能因 `bench/ninfer_kimi_delta_attention_bench` 的链接错误返回非零（b200 构建排除 `mxfp8.cu`，该 bench 的 `traffic.h` 仍引用它）。它与 122B 无关，`release` 构建不受影响；需要 dev 构建里的测试目标时忽略该 bench 即可。

## 3. 权重准备

本模型没有官方发布的 `.ninfer` artifact：从本地 ModelOpt NVFP4 checkpoint 用内置配方转换。checkpoint 需包含 `config.json`、`generation_config.json`、tokenizer、`chat_template.jinja` 与权重分卷；tokenizer、chat template 与 generation 配置会随转换自动写入 artifact。

```bash
python3 -m tools.convert \
  --model /path/to/nvfp4-checkpoint \
  --recipe qwen3_5_122b_nvfp4 \
  --name qwen35-122b \
  --out "$ARTIFACT"
```

- `--name` 决定服务暴露的 model id（`/v1/models` 返回的 id），按需命名；它不选择内核。
- 该配方只转换 text 组件（122B 无 MTP、无视觉），NVFP4 权重原样导入；GDN 的 q/k/v/z/output 投影转成带逐行 FP32 scale 的 E4M3（B200 tcgen05 W8A8 路径），词表头为 Q8/BF16。表示细节见[权重转换](weight-conversion.md)。
- 转换耗时与磁盘开销主要在读写约 30 GB/份的 checkpoint 与 artifact，预留两倍空间。

转换完成后核对 artifact 身份：

```bash
python3 -m tools.artifact.inspect "$ARTIFACT"
# 输出应包含 name: qwen35-122b（或你的 --name）
# provenance.recipe: qwen3_5_122b_nvfp4，sources.base.path 指向你的 checkpoint
```

## 4. 服务部署

单卡启动（性能验收使用的服务参数）：

```bash
CUDA_VISIBLE_DEVICES=$GPU build/b200-release/apps/ninfer-serve "$ARTIFACT" \
  --host 127.0.0.1 --port "$PORT" --device 0 \
  --max-context 2042 --kv-dtype fp8
```

| 参数 | 说明 |
|---|---|
| `CUDA_VISIBLE_DEVICES=$GPU` + `--device 0` | `--device` 是环境变量过滤**之后**的卡序号；只暴露一张卡时恒为 0 |
| `--max-context 2042` | 单请求输入+输出的 token 上限。2042 是验收 harness 数据集的配置值；自部署时按业务需要设置，更大的值会占用更多共享 Context 池 |
| `--kv-dtype fp8` | KV 表示；全部基线数字在此设置下测得 |
| `--max-concurrency`（可选） | 不加（默认 0）：按上下文容量自动拟合 lane 数（本模型在 2042 上下文下约 700 条），lane governor 按 decode 节拍约束常驻 lane，优先保证 TPOT；显式 `N`：固定 N 条常驻 lane、不受 governor 约束，优先吞吐。验收 harness 的吞吐模式用 `--max-concurrency 360` |

启动日志会打印资源配置与 Context 池容量；就绪后探测：

```bash
curl "http://127.0.0.1:$PORT/v1/models"
# 发一条预热请求（首次推理含图捕获）：
curl "http://127.0.0.1:$PORT/v1/chat/completions" \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen35-122b","messages":[{"role":"user","content":"你好"}],"max_tokens":32}'
```

请求体里的 `model` 用 `/v1/models` 返回的 id（即转换时的 `--name`）。服务默认只监听回环地址；常驻部署用 `--config FILE` 走 TOML，全部字段见 [ninfer.example.toml](../ninfer.example.toml) 与[启动配置](startup-configuration.md)。

## 5. 正确性验证

### 5.1 困惑度

```bash
CUDA_VISIBLE_DEVICES=$GPU build/b200-release/apps/ninfer-perplexity --quick "$ARTIFACT"
```

语料是仓库内置的 [ninfer-ppl-1m-v1](../eval/corpora/perplexity-1m/README.md)；`--quick` 每个领域取 `00` 号流，共 124 个 4096-token 窗口、261,170 个评分 token，纯 prefill 路径。

| 项 | 基线值（提交 `4ab8b02a`） |
|---|---|
| 困惑度 | 3.870522（参考 3.867259，+0.084%；差值来自 BF16 GDN state 的设计取舍） |
| 重复运行 | 逐位相同 |
| 评分速率 | 约 19,700 token/s，窗口耗时中位数约 94 ms |

建议判据：与参考值偏差 < 1%，且重复运行逐位一致。第一轮（`3a61e41f`）为 3.867882（+0.016%）。

### 5.2 测试套件

```bash
ctest --test-dir build/b200-dev -R "lane_governor|scheduler|linear_sm100|moe_block_scaled_122b|decode_graph"
CUDA_VISIBLE_DEVICES=$GPU build/b200-dev/tests/ninfer_softmax_attention_test   # 同时覆盖 sampling 与 gated_delta_net
NINFER_TEST_ARTIFACT="$ARTIFACT" ctest --test-dir build/b200-dev -R "preemption_real|zero_suffix_real"
```

已知的既有失败（与 122B 部署无关，在基线 `3a61e41f` 上同样失败，遇到时不影响验收）：

- 6 个 nvfp4 用例报 "nvfp4 linear: mma.sync is not available on b200"：`linear_projection_nvfp4`、`linear_split_nvfp4`、`linear_add_nvfp4`、`linear_swiglu_nvfp4`、`gdn_input_proj_conv_snapshot`、`gdn_input_proj_conv_record`。
- 真实 artifact 测试中的 `native_transactions` 与 `packed_prefill_real`（fixture 与 BF16 state 的既有不匹配）。

### 5.3 生成 sanity（可选）

对若干真实 prompt 各发 `n=8` 个采样，检查输出非空、无替换字符（`�`）、无重复塌缩。这是文本合理性检查，不能替代 5.1/5.2 的数值证据。

## 6. 性能验证

性能测量要求独占目标 GPU：启动服务前确认显存占用已释放（`nvidia-smi --query-gpu=memory.used --format=csv,noheader -i $GPU` 低于 2000 MiB），任一时刻只跑一个服务进程。

### 6.1 定批 decode（decode 步长）

这是与 sglang 对比 decode 性能的主口径：N 条流同时发起、各生成 1200 token，全部 N 行常驻的窗口内每条流的 TPOT 中位数就是 N 行的 decode 步长。先启动固定 lane 的服务（显式 `--max-concurrency` 关闭 governor，保证 N 行全部常驻）：

```bash
CUDA_VISIBLE_DEVICES=$GPU build/b200-release/apps/ninfer-serve "$ARTIFACT" \
  --host 127.0.0.1 --port "$PORT" --device 0 \
  --max-context 2042 --kv-dtype fp8 --max-concurrency 128 --gpu-timing
```

就绪并预热后运行测量脚本：

```bash
python3 -I tools/bench/run_serve_fixed_batch.py \
  --base-url "http://127.0.0.1:$PORT" \
  --rows 32,48,56,64,72,96 --max-tokens 1200 \
  --output .agent-tmp/fixed_batch/run.json
```

脚本只走公开 HTTP：每条流使用预先建好的连接、同时释放，采样为 temperature 0.9、top_p 0.9、top_k 20、显式 presence penalty 0（显式设置保证跨引擎可比）。token 数取 usage 计数，服务未回 usage 时退化为事件计数并标记为估计。

基线（提交 `4ab8b02a`，对照 sglang 0.5.15.post1，同一负载）：

| 行数 | 新版 TPOT (ms) | sglang (ms) | 差值 |
|---:|---:|---:|---:|
| 32 | 10.38 | 10.77 | -3.6% |
| 48 | 11.85 | 12.36 | -4.1% |
| 56 | 12.53 | 13.10 | -4.4% |
| 64 | 13.09 | 13.56 | -3.5% |
| 72 | 13.89 | 14.13 | -1.7% |
| 96 | 15.42 | 15.66 | -1.5% |

两次重复相差 < 0.6%。

### 6.2 端到端锁定 harness（验收口径）

官方验收使用外部的负载测试脚本（验收机位于负载测试目录，下文以 `$LOAD_TEST` 指代）：客户端 `benchmark_stream_server_ts.py` 与数据集 `infer_data_formatted_online.jsonl`（2000 条多轮对话），并发 130 的闭环、`max_tokens=15`、temperature 0.9、top_p 0.9、每请求 n=4（或 n=8）个采样、超时 600 s。服务参数即第 4 节的启动命令（`--max-context 2042 --kv-dtype fp8`，不加 `--max-concurrency`）。

```bash
python3 "$LOAD_TEST/scripts/benchmark_stream_server_ts.py" \
  --base-url "http://localhost:$PORT/v1" --api-key dummy \
  --model qwen35-122b \
  --data-path "$LOAD_TEST/data/infer_data_formatted_online.jsonl" \
  --output-file bench.json --max-concurrent 130 --max-tokens 15 \
  --temperature 0.9 --top-p 0.9 -n 4 --request-timeout 600
```

官方封装脚本固定 n=4，可用 `NINFER_SERVE_EXTRA` 追加服务参数（吞吐模式示例）：

```bash
NINFER_SERVE_EXTRA="--max-concurrency 360" \
  bash "$LOAD_TEST/scripts/ninfer_bench.sh" --require-complete 2000
```

基线（2000/2000 成功、0 失败）：

| 构建 / 服务配置 | n | req/s | 平均 TPOT (ms) | 对照 sglang |
|---|---:|---:|---:|---|
| `3a61e41f` 默认（361 lane） | 4 | 94.00（官方验收单次 95.26） | 36.02 | sglang 61.0 req/s / 8.48 |
| `4ab8b02a` 默认（governor） | 4 | 82.67 | 7.85 | 吞吐 +35.5%，TPOT -7.5% |
| `4ab8b02a` 默认（governor） | 8 | 62.92 | 4.26 | 吞吐 +68.1%，TPOT -4.9% |
| `4ab8b02a` `--max-concurrency 360` | 4 | 122.49 | 26.90 | 吞吐模式 |
| `4ab8b02a` `--max-concurrency 360` | 8 | 89.39 | 9.64 | 吞吐模式 |

解读要点：默认（governor）配置用一部分吞吐换 TPOT——常驻请求约 74 个（n=4），请求在队列中等待使平均 TTFT 升到约 1.28 s（sglang 为 1.78 s），但 E2EL 变化小得多；以吞吐为验收口径时显式加 `--max-concurrency 360`。

### 6.3 仓库自带服务基准

不依赖外部 harness 的两组补充口径（自动起停服务、保存原始结果，参数语义见 [tools/bench](../tools/bench/README.md)）：

```bash
# 串行语料：短/长 prefill 与结构化输出的单请求时延
python3 tools/bench/run_serve_corpus.py \
  --serve build/b200-release/apps/ninfer-serve \
  --artifact qwen35-122b="$ARTIFACT" \
  --mode mtp0 --kv-dtype fp8 \
  --output .agent-tmp/corpus/run

# 并发：decode-saturation（饱和 decode 吞吐）与 corpus-makespan（语料总耗时）
python3 tools/bench/run_serve_concurrency.py \
  --serve build/b200-release/apps/ninfer-serve \
  --artifact qwen35-122b="$ARTIFACT" \
  --mode mtp0 --kv-dtype fp8 \
  --suite decode-saturation --concurrency 1 --concurrency 8 \
  --output .agent-tmp/serve-bench/run
```

注意：本模型必须显式 `--mode mtp0`（artifact 无 MTP 组件，默认的 mtp3 点会启动失败）。TTFT 剖析用 [run_serve_ttft_campaign.py](../tools/bench/ttft/README.md)，但内置 profiles 针对 27B 模型，用于 122B 需要通过 `--profile-config` 提供 JSON 配置并核对 tokenizer/template。

### 6.4 与 sglang 的对照部署（可选）

sglang 基线（0.5.15.post1）用同一个 NVFP4 checkpoint（`$CHECKPOINT`，即第 3 节转换的源），t1 基线参数启动：

```bash
python3 -m sglang.launch_server --model-path "$CHECKPOINT" --tp-size 1 \
  --mem-fraction-static 0.90 --context-length 2042 --quantization compressed-tensors \
  --kv-cache-dtype fp8_e4m3 --cuda-graph-max-bs 256 --chunked-prefill-size 16384 \
  --max-prefill-tokens 32768 --schedule-conservativeness 0.3 \
  --mamba-scheduler-strategy extra_buffer --attention-backend triton \
  --prefill-attention-backend flashinfer --max-running-requests 170 \
  --mamba-ssm-dtype bfloat16 --mamba-full-memory-ratio 4.0 --max-total-tokens 2000000 \
  --enable-prefill-delayer --prefill-delayer-max-delay-passes 10 \
  --prefill-delayer-max-running 80 --enforce-piecewise-cuda-graph \
  --piecewise-cuda-graph-max-tokens 16384 --decode-log-interval 1 \
  --host 127.0.0.1 --port "$SG_PORT"
```

对比时注意采样参数不对称：harness 客户端不发 top_k 与 penalty，两个引擎各自补默认值（ninfer 用模型预设 top_k 20、presence penalty 1.5；sglang 用 generation_config 的 top_k 20、无 penalty）。定批 decode 的负载两边显式一致，不受此影响。

## 8. 注意事项

- 性能测量独占 GPU：任一时刻一个服务进程，启动前等显存释放（< 2000 MiB）；每 sample 用新进程并在测量前完成预热。
- 基线数字对应 `3a61e41f`（第一轮）与 `4ab8b02a`（第二轮）两个提交，其它代码版本不直接套用。
- 默认（governor）与显式 `--max-concurrency` 是两种工作点：前者优先 TPOT，后者优先吞吐；比较代码版本时先对齐工作点。
- 困惑度与生成 sanity 只覆盖 prefill 数值路径；decode 路径的数值证据是各 op 测试套件（5.2 节）。
